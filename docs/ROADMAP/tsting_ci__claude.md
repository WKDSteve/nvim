Commits prüfen: testing ci commit. Wenn du einen Commit reviewst oder prüfen sollst, ob er etwas kaputt macht, prüfe ihn mit scripts/test.sh ci commit <sha> im Repo (ohne Template-Skript: nvim -n -i NONE --headless -u NONE -l "$REPOS_DIR/testing.nvim/scripts/testing.lua" ci commit <sha> --root=<repo>), nie mit scripts/test.sh oder testing ci im Arbeitsbaum. Mehrere: ci commit <a> <b> oder --range=<von>..<bis>. Der Befehl prüft jeden Commit in einem eigenen Git-Worktree, andere Chats im selben Checkout stören also nicht, und er vergleicht Rot mit dem Parent. Lies die erste Zeile: CLEAN und KNOWN-RED heißen „der Commit macht nichts neu kaputt“ (Exit 0), REGRESSION listet darunter die neuen Befunde (new …, Exit 1; beheben oder melden), UNCLASSIFIED (Root-Commit oder Basis lief nicht) prüfst du von Hand, DOCS-ONLY lief bewusst nicht. Lass nie einen Commit aus, weil eine Suite rot ist; known-red ist ein Ergebnis, kein Grund zum Überspringen, und im Bericht steht das Urteil je Commit. Ein schon geprüfter Commit kommt sofort aus dem Gedächtnis ((kept result)); --force nur, wenn sich Werkzeuge oder Abhängigkeiten geändert haben. --json=<datei> liefert das Dokument testing-ci-commit/1, --keep lässt die Worktrees zum Nachstellen stehen (die rerun-Zeile nennt den Befehl). Auf der Workstation läuft es nicht (wie jeder Lauf).
